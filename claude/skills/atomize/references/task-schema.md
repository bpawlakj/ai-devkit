# Task & Index Schema (canonical reference)

This doc is the single source of truth for the shape of `T-NNN-<slug>.md` task files and the derived `index.md` view inside `docs/work/<NNN>-<slug>/` initiative folders.

`/atomize` reads and writes these files; both initial atomization and reconciliation flows conform to the format below.

## Task file (`T-NNN-<slug>.md`)

Each task file represents one atomic unit of work derived from `plan.md`. Tasks are referenced by their `T-NNN` identifier in the index and in cross-task dependency links.

### Frontmatter (load-bearing)

```yaml
---
id: T-001                              # zero-padded 3-digit, unique within the initiative folder
title: Add OTel SDK dependencies       # one-line title (≤ 80 chars)
status: pending                        # pending | in-progress | done | obsolete
plan: ../plan.md                       # relative path to parent plan (always ../plan.md)
created: 2026-05-19                    # YYYY-MM-DD, set on file creation
completed: null                        # YYYY-MM-DD when status → done; null otherwise
commit: null                           # git SHA of implementing commit; null if not yet implemented
depends_on: []                         # list of T-NNN ids this task waits on
blocks: [T-002, T-003]                 # list of T-NNN ids that wait on this
plan_anchor: null                      # optional: heading or section in plan.md this task derives from
---
```

### Status semantics

- **`pending`** — work not started. Default on initial creation.
- **`in-progress`** — work started but not complete. User-managed; `/atomize` doesn't flip this automatically.
- **`done`** — work complete. The implementing commit SHA should be in `commit:`. Reconciliation runs verification heuristics against this status.
- **`obsolete`** — task no longer applies (e.g. removed from plan). Files are NOT deleted; status flip preserves history. New work that supersedes obsoleted tasks references them in the body.

### Body sections (suggested but not enforced)

```markdown
## Scope

What this task changes. Files, functions, configs touched. Specific enough that a reviewer can verify completion by diffing.

## Approach

How to implement. References to relevant existing patterns in the codebase. May reference plan.md sections.

## Acceptance

What "done" looks like. Observable behavior, test cases, manual verification steps.
For failure/edge cases, "If <trigger>, then <expected response>" phrasing keeps the criterion testable.

## Notes

(Optional) Surprises encountered, decisions deviating from plan, follow-ups.
```

User-added sections (debug notes, learnings, links) are preserved on reconciliation — `/atomize` only edits schema-controlled frontmatter fields.

## Index file (`index.md`) — DERIVED VIEW

The index is regenerated from T-*.md frontmatter on every `/atomize` run. Do NOT hand-edit; changes will be overwritten.

### Format

```markdown
# Index — <Initiative slug from folder name>

Generated by `/atomize` on YYYY-MM-DD. T-*.md frontmatter is the source of truth; this file is a derived view.

## Done

| ID | Title | Completed | Commit |
|---|---|---|---|
| T-001 | Add OTel SDK dependencies | 2026-05-10 | abc1234 |
| T-002 | Tracing config | 2026-05-12 | def5678 |

## In flight

| ID | Title | Depends on |
|---|---|---|
| T-003 | Metrics bridge | T-001 |

## Pending

| ID | Title | Depends on | Blocked by status |
|---|---|---|---|
| T-004 | Dashboard | T-003 | T-003 in-progress |

## Obsoleted

| ID | Title | Reason |
|---|---|---|
| T-000 | (none yet) | — |

## Verification log

Last reconciliation: YYYY-MM-DD HH:MM
- T-001 status=done — verified via commit abc1234 + file presence ✓
- T-002 status=done — verified via commit def5678 + file presence ✓
- T-003 status=in-progress — user-asserted, not auto-verified
```

### Section semantics

- **Done** — `status: done` in T-*.md frontmatter. Verification log records how completion was confirmed.
- **In flight** — `status: in-progress`. User-managed; not auto-verified.
- **Pending** — `status: pending`. Blocked-by column derives from `depends_on` + the dependency's current status.
- **Obsoleted** — `status: obsolete`. Reason text comes from the body of the obsoleted task or a follow-up entry.
- **Verification log** — appended on each reconciliation run. Records: per `status: done` task, what evidence supported the claim (commit, file existence, user assertion).

## Reconciliation heuristics (for `/atomize` reconciliation mode)

When verifying that `status: done` claims match real code state, `/atomize` applies three layers in order:

1. **Git log check** — `git log --oneline -- <files mentioned in T-*.md scope>` AND `git log --grep "T-NNN"` to find commits matching the task. If a commit is found and the SHA matches `commit:` frontmatter, mark verified.
2. **File presence check** — extract file paths from the task's `## Scope` section; verify they exist in the working tree. If any are missing, flag as unverified.
3. **User assertion** — if (1) and (2) are ambiguous (no commit reference, no specific file paths), ask the user: "T-NNN claims status: done but I can't auto-verify. Confirm completion or revise to in-progress?"

Verification results are logged in `index.md`'s `## Verification log` section so future runs can see what was confirmed and when.

## Drift detection

If a maintainer renames a frontmatter key or restructures the body convention, update this doc FIRST, then `/atomize` SKILL.md, then any existing T-*.md files via `/atomize <folder>` reconciliation.
