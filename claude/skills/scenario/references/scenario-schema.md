# Scenario Schema (canonical reference)

Single source of truth for the artifacts `/scenario` writes and `/e2e-run`
reads. Two coupled artifacts per scenario: a **scenario plan** (`.md`,
human-reviewable, carries the dependency links) and one or more **generated test
files** (`.spec.ts`, committed, runnable). The plan is the durable record; the
test is generated from it.

## Directory layout (in the TARGET project, not ai-devkit)

```
tests/e2e/
  scenarios/<slug>.md            # scenario plan (this schema)
  web/<slug>.spec.ts             # generated Playwright web test (browser)
  api/<slug>.api.spec.ts         # generated Playwright API test (request fixture)
  playwright.config.ts           # offered on first run if absent
  extensions.md                  # written by /e2e-run when an API extension is enabled
```

`tests/e2e/` is deliberately separate from a project's unit `tests/` so the two
never collide. Override with `--dir` (default stays `tests/e2e/`).

## Scenario plan file (`tests/e2e/scenarios/<slug>.md`)

### Frontmatter (load-bearing — `/e2e-run` parses this)

```yaml
---
slug: checkout-happy-and-edge           # kebab-case, unique within scenarios/
title: Checkout — optimistic + pessimistic paths
initiative: docs/work/004-checkout/      # initiative folder, or null
depends_on: [T-012, T-013]               # T-NNN tasks this scenario exercises (mirrors task-schema)
layers: [web, api]                       # subset of {web, api} — which test files exist
tags: [optimistic, pessimistic]          # path types present (drives --grep)
base_url_hint: http://localhost:3000     # advisory only; tests read it from env/config, never hardcode
generated:                               # every file generated from this plan
  - tests/e2e/web/checkout-happy-and-edge.spec.ts
  - tests/e2e/api/checkout-happy-and-edge.api.spec.ts
created: 2026-06-04                       # YYYY-MM-DD
---
```

`depends_on` and `initiative` are the back-links. `/e2e-run` resolves scope from
them: "run every scenario whose `depends_on` contains T-012" or "run every
scenario under initiative 004".

### Body sections

```markdown
## Source

Where the scenario came from: the T-NNN ## Acceptance block, an initiative plan
section, product-spec FRs/User Stories, or a freeform description. Quote the
acceptance criteria verbatim — they are the assertion oracle.

## Optimistic paths

The expected-success flows. Each path is a numbered, observable sequence ending
in an assertion drawn from the source (not from observed app output).

### OPT-1: <name>
1. <action — user-visible or API call>
2. ...
- **Assert**: <observable outcome / persisted state, sourced from acceptance criteria>

## Pessimistic paths

The failure/edge flows the system must handle gracefully. Cover the standard
families (include those that apply; name why any are N/A):
invalid input · auth/permission failure · empty / boundary state ·
duplicate / conflict · upstream/server error · timeout / slow response ·
concurrent modification.

### PES-1: <name>
1. <action that triggers the edge>
- **Assert**: <controlled failure the system must produce — error message, status
  code, no state mutation, etc.>
```

## Generated test files

Each generated `.spec.ts` opens with a back-link banner (first lines), so a
reader of the test can find its plan and the work it traces to:

```ts
// scenario: tests/e2e/scenarios/<slug>.md
// initiative: docs/work/004-checkout/ | tasks: T-012, T-013
// Generated by /scenario on 2026-06-04. Edit the scenario plan and re-run /scenario,
// or hand-edit and keep the banner in sync. Do NOT auto-heal — review every change.
```

### Path-type tags (drive `/e2e-run --grep`)

Tag every test with its path type using Playwright's `tag` annotation so
`/e2e-run --grep @optimistic|@pessimistic` selects subsets:

```ts
import { test, expect } from '@playwright/test';

test('checkout succeeds with a valid cart', { tag: ['@optimistic'] }, async ({ page }) => { /* OPT-1 */ });
test('checkout rejects an expired card',     { tag: ['@pessimistic'] }, async ({ page }) => { /* PES-1 */ });
```

### Web layer (`web/<slug>.spec.ts`)

- Use role-based locators first (`getByRole`, `getByLabel`), then `data-testid`,
  then CSS as a last resort. Selectors marked `// TODO: verify selector` when the
  live-grounding step (MCP) was skipped.
- Read `baseURL` from `playwright.config.ts` / env — never hardcode a host.

### API layer (`api/<slug>.api.spec.ts`)

- Use Playwright's `request` fixture (no browser). Canonical stateful flow:
  seed/login via API → act → assert backend state via API → reset via API.
- Auth tokens from env/fixtures, never literals (mirrors the security-baseline
  SEC-01 rule in `/implement`).

## Invariants

- **Assertion oracle = acceptance criteria / spec, never observed implementation
  output.** A test that asserts what the code currently does only cements bugs.
- **No hardcoded secrets or hosts.** Env / config only.
- **The plan `.md` is the human-review gate.** `/scenario` never writes test code
  before the user confirms the plan. `/e2e-run` never regenerates tests on
  failure. All test changes are human-reviewed.
- **`generated:` is exhaustive.** Every file `/scenario` writes is listed there,
  so `/e2e-run` and reconciliation know the full footprint of a scenario.
